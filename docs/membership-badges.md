# 量立方社区会员与 Badge 体系（方案草案）

版本：v1 · 2026-10-10。此文档是产品与权限设计，不代表账号或申请功能已经上线。

## 1. 目标与原则

- 一个账号可以同时拥有多个身份：机构代表、校园大使、FatQat 贡献者并不互斥。
- Badge 说明已核实的身份或贡献；具体操作权限由服务端根据当前有效身份判定。
- 所有稿件和活动都经过社区编辑/运营审核。拥有申请权限不等于拥有直接发布权限。
- Badge 展示尽量简洁；公开资料由本人选择，私密邮箱、学校证明和审核记录不公开。
- 已出现在首页的共建伙伴名单是邀请与核验线索，不自动等于已通过会员认证。

## 2. 身份与权限

所有人可以浏览公开动态和活动。注册会员可以维护资料、关联 GitHub、保存草稿和查看自己申请的状态。

| 身份 / Badge | 获得方式 | 主要能力 | 归属与上限 |
| --- | --- | --- | --- |
| 已认证共建单位 | 预登记域名的机构邮箱验证，或机构材料人工审核 | 公开机构主页；管理本机构代表提名；查看本机构申请 | 归属机构，持续有效但需定期复核 |
| 共建单位代表 | 已认证机构提名，社区首次核准 | 申请社区动态投稿；申请主办/联合主办（Host）或赞助（Sponsor）社区活动 | 每家机构最多 2 个有效名额；个人账号可持有 1 个有效代表名额 |
| 校园大使 | 在校身份验证、简短申请与社区审核 | 申请校园活动支持；申请社区动态投稿 | 归属个人，关联一所当前学校；每学年复核 |
| FatQat 贡献者 | 关联 GitHub 并核实合并贡献 | 展示贡献等级；提交贡献证明与更正申请 | 归属个人；代码贡献本身不自动开放社区发布权限 |
| 社区编辑 / 运营（内部） | 社区任命 | 审稿、活动评估、身份审核、撤销与申诉处理 | 采用独立后台权限，不作为公众升级目标 |

一人多身份时权限取并集。例如某位校园大使也是共建单位代表，可以提交两类申请；每次申请都必须选择对应身份，审核记录保留该身份快照。

## 3. 认证与生命周期

### 共建单位

1. 机构先在后台登记名称、官网和可使用的邮箱域名。现有 `data/partners.json` 可作为候选清单，但不能直接作为已认证清单。
2. 申请者使用该域名邮箱收取一次性验证码，验证邮箱控制权；同名域名、公共邮箱、学校/集团共用域名、子公司与机构名称不一致的情况转人工审核。
3. 第一位机构管理员由社区审核确认。之后该管理员可提名、替换或撤销代表；首次提名仍由社区确认。
4. 最多同时有 2 位状态为 `active` 的代表。更换名额采用“先撤销旧代表，再启用新代表”，避免短暂超额。
5. 机构管理员与代表定期邮件确认关联；邮箱失效、离职或机构撤销时立即冻结相应权限，已有已发布内容不自动删除。

机构邮箱只证明邮箱控制权。没有预登记域名时，申请处于 `pending_review`，不自动颁发 Badge。

### 校园大使

申请者填写学校、院系/身份、校园计划，并通过学校邮箱或人工材料核验。批准后获得基础校园大使 Badge；每学年确认仍具备在校身份。毕业者保留历史贡献展示，但校园活动支持申请权限转为失效，除非另有社区身份。

### FatQat 贡献者

会员通过 GitHub 登录或关联账号。系统仅采纳 `spaceqat/fatqat` 及后续明确纳入的官方仓库中可核验的贡献；合并 PR、已接受 Issue、代码评审与发布记录由维护者确认。贡献可由系统建议计分，争议与重大贡献由维护者复核。GitHub 名称变更不影响会员 ID。

所有 Badge 授予记录包含 `awarded_at`、`awarded_by`、`evidence`、`status`。状态为 `pending`、`active`、`suspended`、`revoked`、`expired`；权限只从 `active` 状态计算，状态变更写入审计日志。

## 4. 等级设计

身份 Badge 与贡献等级分离：共建单位代表不因积分升级，校园大使和 FatQat 贡献者可以升级。积分仅来自有证据、已审核的贡献；同一项工作不重复计分，联合署名按实际参与核定。

### 校园大使

| 等级 | 条件（累计审核积分） | 可见名称 |
| --- | --- | --- |
| 基础 | 完成身份与计划审核 | 校园大使 |
| L1 | ≥10 分 | 活跃校园大使 |
| L2 | ≥30 分，至少完成 2 场活动或 2 篇稿件 | 校园共建者 |
| L3 | ≥70 分，至少跨 2 个学期持续参与，社区复核 | 校园引领者 |

建议计分：完成并提交复盘的校园活动 8 分；联合筹办活动 5 分；经编辑发布的原创稿件 4 分；经确认的教程/答疑工作 2 分。单次活动重复宣传不单独计分。校园活动支持申请权限从基础等级开始，不需等升级。

### FatQat 贡献者

| 等级 | 条件（累计审核积分） | 可见名称 |
| --- | --- | --- |
| Entry | 首个合并 PR 或首次被维护者接受的实质贡献 | FatQat Entry |
| L1 | ≥10 分 | FatQat Contributor |
| L2 | ≥30 分，贡献涉及至少 2 个独立改进 | FatQat Builder |
| L3 | ≥80 分，持续参与并经维护者复核 | FatQat Core Contributor |

建议计分：合并的实质代码 PR 5–10 分；文档、示例或测试 PR 2–5 分；已确认并有复现信息的缺陷报告 2 分；被采纳的代码评审 2 分；主导一次正式发布 8 分。维护者决定具体分值并记录原因；PR 数量本身不决定等级。`Core Contributor` 不是仓库写权限或合并权限，维护者权限另行授予。

历史最高等级可保留在个人档案；活跃标识需要最近 12 个月有至少一项已核实贡献。无活跃记录时显示“历史等级”，不抹除旧贡献。发现刷分、冒认或违规内容时可撤销相关积分并支持申诉。

## 5. 申请工作流

### 社区动态投稿

代表或校园大使进入“申请发布稿件”，选择使用的有效身份，填写标题、摘要、正文或稿件链接、配图来源、机构/作者署名、是否涉及赞助和联系人。状态为 `draft → submitted → in_review → revision_requested / approved / rejected → scheduled → published`。编辑可要求修改；正式发布仍进入网站现有的 `data/news.json` 工作流，保留外部原文链接。发布前展示最终预览供作者确认署名与链接。

### 社区活动 Host / Sponsor

共建单位代表可分别申请主办/联合主办（Host）或赞助（Sponsor）。表单包含活动主题、时间地点、受众、预算或资源、社区需要承担的工作、品牌露出、联系人。社区审核后再约定执行安排；活动完成后提交复盘与照片授权。赞助内容在活动页和文章中明确标注。

### 校园活动支持

校园大使提交学校、活动目标、预计人数、日期、所需讲者/教材/宣传/设备/费用、校园审批进度。运营人员给出 `approved`、`need_more_info` 或 `declined`，批准后记录实际支持项与复盘结果。积分在复盘审核通过后发放。

所有申请列表只对申请者、其有效机构管理员（机构申请）及负责审核的工作人员可见。邮件通知只提示状态变化，完整内容在登录后查看。

- 新增机构主页：机构标识、简介、已认证状态、最多两位自愿公开的代表、已发布内容和活动。代表资料默认不公开。

## 7. 技术边界与交付顺序

当前站点是 GitHub Pages 静态 HTML，社区动态由 `data/news.json` 读取。静态前端不能安全保存账号、验证邮箱或强制审核权限。建议保留现有展示站，在独立社区应用（例如 `community.space-qat.com`）承载登录、申请和后台审核；官网的会员入口链接到该应用。公开的已认证机构与 Badge 摘要可通过只读接口或构建时导出回官网。

最小数据实体：`users`、`organizations`、`organization_domains`、`affiliations`、`badge_awards`、`contributions`、`applications`、`articles`、`events`、`audit_log`。所有修改权限在服务端检查，不能只依据前端显示的 Badge。

实施分三阶段：

1. **说明与试运行**：完成规则页和申请入口；后台人工登记首批机构域名、代表和校园大使；不做自动积分。
2. **会员与申请**：上线账号、机构邮箱验证、代表名额管理、稿件/活动表单和审核后台；与现有动态清单对接。
3. **贡献升级**：接入 GitHub 贡献核验、校园积分台账、等级进度、申诉和数据导出。

上线验收重点：机构无法通过未经登记的近似域名自领 Badge；第三位代表无法启用；撤销代表后立即失去申请权限；未审核稿件不会出现在公开动态；“减少动态效果”时 Badge 动画不播放；个人资料公开范围符合本人设置。

## 8. 待项目负责人定稿的规则

- 首批机构域名及机构管理员名单；集团与子公司是否共用机构名额。
- 校园大使的招募范围、每学年复核时间，以及活动支持的预算上限。
- 投稿审核负责人、时限、赞助披露模板和对外署名规范。
- FatQat 官方计分仓库范围与最终维护者复核人。

以上配置不影响方案落地，但需要在开放申请前明确并录入后台。
